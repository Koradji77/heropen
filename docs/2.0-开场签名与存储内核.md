# heropen 2.0 · 开场签名 与 存储内核（产品语义定稿）

> 本文是 2.0 两个「存在感 / 落档」能力的**产品语义定稿**。代码以本文为准，改行为前先改本文。

## 一、开场签名

**定义**：每次对话开场、agent 真正开始办事之前，由 heropen **自动塞进上下文**的一小段品牌 + 状态文字。
不是用户自己敲命令，也不是打开面板。

**典型形态（示意）**：

```
heropen 已就绪 · 本地记忆 187 条 · 距上次对话约 3 小时 · agent=xiaokai
```

**挂载点**：

- MCP `prime_conversation` 的返回值（贴在**开头**）；
- CLI `bootstrap`（可选，同样在开场打印）；
- 以后「开场自动召回」若做成，签名贴在那一块开头。

**算什么 / 不算什么**：

| 是 | 不是 |
| --- | --- |
| 一行（或两三行）固定格式的「我还在」 | 完整工作台 / 面板 |
| 跟着对话出现，用户不用主动来找 | 托盘图标（那是另一条存在感） |
| 可带条数、时长、agent 名 | 替你做语义检索本身（检索是加分项） |

**2.0 存在感 = 开场签名 + 托盘**：签名管「聊的时候看见」；托盘管「不聊也在任务栏」。

## 二、存储内核：三种模式的写入语义

托盘里「大块 / 一轮一存 / 自动识别」接到 heropen 内核后的落档策略（此前只存偏好、不生效）。

| 模式 | 含义 | 何时写入 heropen | 适合 |
| --- | --- | --- | --- |
| 大块存储（chunk） | 攒一批再落 | 一段对话告一段落 / 缓冲区够长 / 会话结束时，合成较少几条记忆再 add | 闲聊、日常，少打扰、少碎条目 |
| 一轮一存（sentence） | 一轮就落 | 用户（或 assistant）每完成一轮有信息量的话轮，就尽快写成一条 | 调教、拍板、重要约定，宁碎勿丢 |
| 自动识别（auto） | agent / 规则选上面两种 | 闲聊倾向 chunk；出现偏好 / 决策 / 项目事实倾向 sentence | 默认；少让用户手切 |

**必须钉死的边界**（否则三种模式会打架）：

1. 写的仍是 heropen 事实库（SSOT），**不是热层双写全文**。
2. 模式管的是**落档频率与粒度**，**不管检索、不管托盘显示**。
3. `auto` 的判定规则要**可解释**：命中「记住 / 决定 / 路径 / 偏好」等触发词 → `sentence`，否则 `chunk`。
4. **同一 agent 一套模式**；多 agent 可各设各的（托盘已按 agent 分设）。
5. **会话断点（SESSION_SECTION = `⚡ 会话断点`）是例外，永远即时落库，不受存储模式约束。** `session_checkpoint()` 直接调 `add_entry`，不走 `store_memory`。理由：断点是崩溃恢复基础设施，进程在 chunk 攒批 flush 前崩溃就会丢断点、丧失续接能力；它不属于「记忆事实」语义，故不进落档策略。切 `chunk` 也挡不住断点——这是有意设计，不是遗漏。

**一句话**：签名 = 开场自动亮相的一行状态；三种存储模式 = 记忆往 heropen 写时「攒着写 / 句句写 / 智能选」的策略。

## 三、代码落点

| 函数 | 职责 |
| --- | --- |
| `core.build_signature(agent)` | 生成开场签名行 |
| `core.get_storage_mode(agent)` | 读该 agent 的模式（托盘 `_tray_state.json`；env `HEROPEN_STORAGE_MODE` 可覆盖） |
| `core.classify_storage_mode(text)` | auto 判定，返回 `(mode, reason)`，可解释 |
| `core.store_memory(...)` | 写入策略总入口：sentence 直落 / chunk 缓冲 / auto 先判 |
| `core.flush_pending(agent)` | 缓冲区按 section 聚合后真正落库 |

**不静默丢失的保证**：chunk 缓冲落盘在 `~/.heropen/_pending_<agent>.json`，
攒够阈值（默认 6 条）自动落库，且**每次开场（prime / bootstrap）补落上一段攒下的内容**。

## 四、2.0.1 · 每轮自动存档钩子（✅ 已落地，2026-10-06 定稿 → 2.0.1 实现）

**来源**：xiaokai（四号机本环境）实机验证 V2.0 时发现——`sentence` 模式只保证「一旦写入就立即落、不缓冲」，**不自动触发每轮存档**；是否写入的决定权仍在模型（须主动调 `add_memory`）。全仓核实：`session_checkpoint` 调用方仅 2 处（CLI `heropen session` + MCP `session` 工具，均显式）、`store_memory` 调用方仅 1 处（MCP `add_memory` 工具），**无「每轮对话结束自动存档」的宿主 / 网关钩子**。

**产品结论**：这是「产品期望超出已钉规格」，非 bug。已钉规格中 sentence 的限定词是「**有信息量**的话轮」，当时定的就不是每轮必存。要达到 Eddie 期望的「一步一存、轮轮不落」，必须在宿主 / 网关层加钩子。

**规格（实现时以此为准）**：

- **触发位置**：每轮 `assistant` 回复**完成后**（宿主 / 网关侧，不依赖模型自觉）。
- **内容**：本轮 `assistant` 回复原文（或本轮摘要；由宿主从完整对话上下文提取，不靠模型额外生成）。
- **落库**：调 `core.store_memory(...)`（事实库 SSOT）。**严禁调 `session_checkpoint`** —— 断点表是崩溃恢复基础设施，每轮调会每轮爆一条断点，且语义 ≠ 记忆事实（小凯草案此处有误，已更正）。
- **两层正交**：「每轮自动提交（触发）」与「落档频率（模式）」正交。钩子每轮把本轮内容提交给 `store_memory`，落库时机仍由模式决定 —— sentence 每轮立即落 / chunk 攒批落 / auto 智能选。
- **不污染**：钩子提交走 `source="auto_turn"` 标签，便于与显式 `add` 区分、必要时可整体回滚（heropen 只标不删）。

**代码落点（2.0.1）**：

| 函数 / 工具 | 职责 |
| --- | --- |
| `core.auto_save_turn(agent, content, user_content, section, tags, entry_date)` | 钩子总入口：`user_content`→`用户输入`+`auto_turn,user`、`content`→`对话记录`+`auto_turn`，均走 `store_memory(source="auto_turn")`；空轮跳过；返回 `{saved,buffered,flushed,parts}` |
| `core.AUTO_TURN_SOURCE` | 常量 `"auto_turn"` |
| MCP 工具 `auto_save_turn(content, agent, user_content, section, tags)` | 宿主 / 网关 / 模型侧调用目标，docstring 写明钩子语义与正交关系 |

**触发杠杆（两种路径，任选其一，可并存）**：

1. **宿主 / 网关权威路径（推荐）**：agent 运行循环在每轮 assistant 回复完成后，直接调 `core.auto_save_turn(agent, reply_text, user_content=user_text)`（嵌入 heropen 时）或 MCP `auto_save_turn` 工具（stdio/SSE 客户端）。这是规格原定的「不依赖模型自觉」路径。
2. **模型侧兜底路径（纯 MCP 客户端即开即用）**：因 heropen 是被动 MCP server、无法自行观测话轮，MCP `instructions` 已加一句——**模型每完成回复就调 `auto_save_turn` 把回复原文传进去**。这样即使 host 未接钩子，WorkBuddy 等客户端也能「轮轮不落」。模型传的是自己的真实回复（非额外生成摘要），符合规格。

**双重写入注意**：若 host 已自动调用 + 模型也自觉调用，同一轮会存两份（source 均 `auto_turn`）。按 heropen「只标不删」铁律，少量重复无害；搜索结果会带 `hygiene_flags` 重复风险提示，回滚/合并由用户决定。不静默丢失优先于零重复。
